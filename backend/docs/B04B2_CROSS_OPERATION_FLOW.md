# B04B-2 — Cross-operation dispatch and receipt (isolated development)

Migration 012 adds append-only `operation_dispatches` and `operation_receipts`, with forced tenant/site RLS, immutable history triggers, scoped foreign keys and idempotency/actor references. The reservation FK includes the reserve event type, the output lot and route/work-order provenance. A receipt is linked to its exact dispatch and a newly generated `operation` lot; its parent is the consumed source input lot, while the receipt directly links the authoritative production output lot. There is one destination input lot per partial receipt. No historical records are rewritten. B03C same-operation movement and full-acceptance constraints remain intact.

All commands require a verified actor with `stock.write`, site membership, persistent idempotency and the isolated-development flag. Existing transaction code locks membership and the order, serializing all production, quality, reservations, releases and these movements. The service revalidates approved output, immutable provenance and adjacent internal route; historical output without authoritative provenance remains unavailable. The audit, idempotency, dispatch/receipt and destination lot writes commit or roll back together. RLS and composite FKs defend against missed filters; they do not protect against the documented compromised runtime with arbitrary SQL or fabricated tenant context. Runtime can insert operation lots only in isolated development; migration/owner remains separate.

Reservation accounting: reserve events less release events are outstanding, including quantities already dispatched. A release is limited to the undispatched balance; dispatch permanently consumes that part of the reservation, including after receipt. Hence approved availability is approval minus outstanding reservations; dispatched units are never subtracted twice or returned to availability. In transit is dispatch less receipt. Example: 20 produced, 12 approved, 3 rejected and 5 rework; 8 reserved and dispatched, 5 received: 4 unreserved approved, 0 reserved awaiting dispatch, 3 in transit and 5 physical destination input. This is classification and movement, not new production, automatic quality approval or downstream execution.

The destination `operation-inputs` and existing physical-balances/work-order views show received physical amounts. B04A downstream execution remains disabled: its production ledger and consumption reconciliation support only first-operation material lots and cannot safely consume these new received operation lots or enforce all downstream drawing acknowledgements. Outsourcing, rework processing and customer shipment remain disabled. A quality response's `downstreamReleaseSupported: false` means the quality decision itself does not physically release material; the explicit reservation dispatch is a separate command.

## Isolated verification

Run Node 22 and the full backend tests against a disposable PostgreSQL 16 database with a privileged setup connection. Test cases create random schemas/roles and exercise the actual restricted runtime. Migration/backup tests use PostgreSQL 16 `pg_dump` and `pg_restore`, not an older client. See `evidence/b04b2-postgresql16.tap` for the actual run. The restricted-role scenarios cover the 20/12/3/5 fixture, 8 dispatch/5 receipt, independent retries, concurrent dispatch and receipt, over-release, tenant/site and actor rejection, immutable histories, audit rollback, readiness, disabled downstream production, old histories and existing B01–B04B-1 regressions. Backup/restore and migration setup use privileged roles; runtime request tests do not. Isolated Docker Compose PostgreSQL 16 migration and provisioning completed with exit 0, readiness returned 200 and an unauthenticated session returned 401. These tests use fictional data only.

Production deployment remains NO-GO. Live identity provider, trusted database context under runtime compromise, server hardening, independent production security review and downstream execution remain future work.

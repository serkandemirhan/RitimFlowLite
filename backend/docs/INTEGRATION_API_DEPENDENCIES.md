# Operator / quality integration API dependencies

## Endpoint gap matrix

| Capability | Baseline | Contract in this change |
|---|---|---|
| Assignment and handover | Existing `assignment/operator`, `machine`, `handover` commands | `GET assignment-options`: active operators, machines and assignment history |
| Material input | Existing `POST physical-receipts` consumes an existing allocation | Explicit fictional material intake, allocation and discovery; physical work-order receipt stays a separate existing command |
| Production and quality | Existing balances, lifecycle/results and quality summary/decisions | Production and quality history reads; historical missing provenance is explicitly flagged |
| Next operation | Existing downstream planning, reservation/release, dispatch/receipt, lot and input reads | Order-scoped downstream discovery aggregates existing authoritative projections |

All endpoints are under `/api/v1/sites/{tenantId}/{siteId}/orders/{orderId}` and are registered only in isolated development mode. Bearer identity and authorized site membership are mandatory. The assignment-options read requires `orders.write`; material creation requires `stock.write`; allocation uses `orders.write`, consistent with the existing physical receipt. Other reads require `orders.read`. Mutations require a durable `Idempotency-Key`, perform membership authorization and take the existing order lock inside the database transaction, and write audit entries atomically. `fictional` is explicit and data is not an external supplier receipt or production inventory.

## Frontend contracts

1. `GET /work-orders/{job}/assignment-options` returns `{workOrderId,status,operators:[{id,displayName}],machines:[{id,code,available,assignedWorkOrderId}],assignments:[{id,machineId,operatorId,assignedAt,releasedAt,reason}]}`. Availability is advisory; existing assignment commands revalidate under lock. Active site operators are exposed by a narrowly scoped, hardened security-definer function, without runtime SELECT access to users/membership tables.
2. `POST /fictional-material-receipts` with `{quantity,documentRef,supplier}` returns `{id,receiptId,lotId,quantity,fictional:true,physicalWorkOrderReceipt:false}`. All quantities are pieces; the explicitly fictional supplier/document are demo provenance, not verified real-world documents. Fictional receipts per order are capped at order quantity; compensation and conversions are not supported here.
3. `POST /fictional-material-allocations` with `{workOrderId,lotId,quantity}` returns `{id,orderId,workOrderId,lotId,quantity,fictional:true,physicalReceipt:false}`. Only a tagged fictional material lot and active first internal work order are eligible. Allocation is capped by source balance and work-order plan. To physically receive it, call the existing `POST /physical-receipts` with `{reservationId:id,quantity}`. `GET /fictional-material` exposes material and allocation IDs, quantities and received amounts for reload/retry.
4. `GET /work-orders/{job}/production/history` returns chronological `{events:[{eventId,kind,quantity,actorId,occurredAt,inputLotId,outputLotId,originatingOutputLotId,provenanceStatus}]}`. `GET /work-orders/{job}/quality/history` returns `{decisions:[{id,eventId,inputLotId,outputLotId,outcome,quantity,evidence,actorId,occurredAt,provenanceStatus}]}`. A missing trustworthy historical link is `historical_unreconciled`; it is not created or repaired. Continue using existing `production/balances` and `quality` for current input and outstanding inspection quantities.
5. `GET /downstream-discovery` returns `{supported,reason,nextOperation,workOrders,outputs,dispatches,receipts}`. Outputs reuse `lotView` and contain the reservation history and approved/available quantities. Dispatches include received and in-transit quantities; receipts contain input and source output lot IDs. Existing downstream mutation commands remain authoritative. Unsupported routes fail closed; read summaries do not promise authorization, reservation or physical receipt.

Example for a fictional order: create the receipt (10), allocate 6 to its first work order, call the existing physical receipt (6), assign an operator and machine with the existing commands, then start and record production. Approved output can be planned, dispatched and physically received with the existing downstream contracts; none of those commands happens implicitly. Retry an uncertain mutation with the same idempotency key and payload. 400 denotes malformed input, 403 insufficient scope/capability, 404 unavailable scoped entity and 409 capacity, provenance or unsupported operation. A duplicate document or conflicting idempotency identity can also return 409.

## Security and limitations

Migration 013 adds immutable, forced-RLS `demo_material_sources`, composite provenance FKs and `ritim_eligible_operators` with fixed search path, scope/actor checks and revoked PUBLIC execution. Restricted runtime gets only necessary grants; insertion of demo sources, receipts and reservations is permitted only in isolated development. The documented arbitrary-SQL compromised-runtime context limitation remains. Operator lists do not grant assignment privileges. Drawing acknowledgements, external operations, rework execution, third operations, shipment, real suppliers/purchasing, live IdP and production activation remain unsupported. Receipt/lot and reservation history is not rewritten. First-operation physical receipt after production is still blocked by B03C, and historical legacy lots cannot be treated as fictional onboarding records.

PostgreSQL 16 restricted-runtime integration and migration/backup tests are in `evidence/integration-contracts-postgresql16.tap`. Owner/setup credentials are used only for isolated test setup, migration and backup/restore; API calls use the restricted runtime. Isolated Compose migration/provision/readiness/unauthenticated access is recorded separately. No real data or external service was used.

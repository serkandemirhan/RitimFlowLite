# Recovery encryption key operations

Recovery is enabled only for the explicitly isolated development BFF with `RECOVERY_ENCRYPTION_KEY` (canonical base64 of 32 random bytes) and `RECOVERY_KEY_VERSION`. Supply secrets from a protected external secret store, not source files, logs, browser code or database backups. Generate separate keys for each environment. Preserve version-to-key mapping, access policy and a protected offline backup separately from database backups; perform a restore rehearsal using fictional data and tightly limited access.

The current runtime accepts only one version/key at a time. A missing or malformed key fails configuration; a wrong key or modified ciphertext fails authenticated decryption without deleting or returning plaintext. Existing ciphertext and audit data must be preserved. A test using a random key verifies encryption, restored-key decryption, wrong key and version rejection; this is not an operational backup-restore drill for production secrets.

Do not rotate the key while records encrypted under the old version may still be needed: the current code has no multi-version keyring or verified re-encryption procedure. Implement and test a versioned keyring, controlled staged re-encryption and rollback before production rotation; preserve old keys until all records and required backups no longer need them. Loss of the matching key renders encrypted recovery records irrecoverable. Expiry is metadata only; no cleanup job should delete unresolved records or mandatory audit history. Multi-version rotation, real secret-store backup/restore and retention governance are production blockers.

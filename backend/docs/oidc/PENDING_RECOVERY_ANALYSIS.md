# Pending command recovery: current findings

## Latest implementation — supersedes the historical progress notes below

The premium and integration screens now use authenticated server-side recovery. Migrations 015–018 introduce encrypted command records, encrypted append-only wizard revisions, rejection serialization and explicit acknowledgement. A fixed server command catalog re-enters the normal authorization and idempotency boundary. Recovery is available only with the BFF and explicitly enabled isolated development configuration. The browser stores scoped opaque command identifiers, not new request bodies. Resolved commands remain recoverable until acknowledged. Unresolved records are retained; their expiry timestamp does not trigger automatic deletion.

Legacy `sessionStorage` entries are transferred only after their owner authenticates and explicitly requests migration; the original command identity is preserved, and entries are removed only after durable server registration. Foreign and unrecognized entries are preserved and block the workspace. **Pre-existing plaintext is already readable in that tab before the owner migrates it**, and a different open old-version tab cannot be remotely cleaned. Therefore the non-negotiable shared-profile confidentiality condition cannot be claimed for unmigrated legacy profiles. Owner-assisted migration in every affected tab, or an explicitly approved secure cleanup strategy that addresses uncertain commands, is required before shared-profile use.

Recovery encryption currently requires an externally supplied 32-byte key and version. The service cannot decrypt records after loss of the key; a multi-version rotation/keyring and production secret backup procedures remain outstanding. Production activation is disabled. The sections below are historical notes and may describe earlier intermediate states.

Status: **PARTIALLY IMPLEMENTED; NO-GO**. Migration 015, restricted-role grants and readiness checks create a forced-RLS encrypted recovery table. The internal store and fixed command catalog have focused tests and an opt-in BFF-only isolated-development API. The existing browser journal and workflow still store their command bodies in `sessionStorage`. Do not use the current API UI for confidential data in a shared tab.

The pending journal is `ritim:api-dev:pending-commands:v1`. It stores actor, tenant, site, operation and body, and is directly inspected synchronously by `premium-api.js` and `integration/app.js`. Workflow state is stored under `ritim:api-dev:order-workflow:v1` and its actor/tenant/site scoped variants; it includes order, route, quantities and step outcomes. Replacing only the journal leaves workflow data exposed. Existing `executeCommand` authorizes within a PostgreSQL transaction and uses `(tenant,site,actor,key)` plus a canonical command hash and a completed response as the durable receipt. Recovery must compare the same normalized command semantics before returning a receipt; a matching key by itself is not evidence that a different request is equivalent.

The frontend currently assumes synchronous `journal.begin`, `list`, workflow `read`, `begin`, `revise` and `clear`. Moving storage to an authenticated HTTP API requires an asynchronous state machine and authoritative reload/reconciliation across every production, quality, assignment, drawing, material, transfer and planning consumer, including the older `/integration/` page. A retry must use an explicit server-owned command allowlist and run the ordinary command boundary again, including current membership and resource authorization. It must never replay an arbitrary client-supplied URL or trust a stored actor supplied by the browser.

Old plaintext records present before the upgrade are already readable by anyone who can inspect that same tab. The application cannot retroactively undo that exposure. Their owner must be verified before moving records to the authenticated store; a second user cannot safely vouch for or replay them. The migration must preserve an uncertain command's idempotency identity and obtain durable server acknowledgement before deleting the corresponding plaintext. If the owner cannot authenticate or the server is unavailable, confidentiality and no-loss recovery cannot both be retroactively guaranteed: the UI must fail closed and explain the required owner-assisted recovery rather than erase evidence or claim isolation. The new format must never persist plaintext in browser storage.

`src/recovery-crypto.js` is currently unused by the application. It implements AES-256-GCM with a fresh nonce and associated data binding actor, tenant, site, command, fingerprint and key version; it rejects invalid keys, tampered context/ciphertext and payloads over 32 KiB. The external key must be persisted separately from PostgreSQL, protected by deployment secret management, backed up and versioned; losing it makes unresolved records irrecoverable. This module alone does not enforce access control, retention, idempotency, migration, durable registration or safe retry, and does not protect plaintext still stored by the existing UI.

Remaining implementation: deployed key configuration and key version lifecycle; encrypted durable register/list/read/reconcile/resolve APIs with resource authorization; strict command and resource authorization and concurrency limits; frontend migration away from both plaintext stores; same-tab identity switch and owner-assisted legacy migration; real Keycloak/PostgreSQL 16 tests, restart and quota/failure tests; complete frontend and backend regressions. Key rotation for encrypted recovery records must retain old decryption keys until records are reconciled; unresolved records and audit evidence must not be deleted merely because their preferred retention window passed.

The recovery routes are enabled only when an explicit isolated-development configuration supplies a BFF session and external encryption key. Resource checks include current work-order assignment for production and drawing acknowledgement; exact replay enters the existing authenticated business handler before resolving. Broader resource-specific coverage is still under review. Registration of a recovery record must be followed by the normal business handler, and only an exact authorized replay or equivalent verified receipt may establish completion. The browser must not be migrated to this incomplete interface.

Verification: PostgreSQL 16 full backend suite 114/114 passed on the current backend worktree, including the migration, existing domain regressions, recovery crypto/catalog and restricted-runtime store tests. The first migration regression exposed two hardcoded version expectations and one hardcoded migration count; these were updated for 015. The failed first run is retained at `/tmp/ritim-recovery-current.tap`; the passing run is [recovery-backend.tap](recovery-backend.tap). No real OIDC/frontend acceptance was run for this incomplete recovery implementation.

## Subsequent implementation in progress

Migrations 015–016 add forced-RLS actor/site-scoped encrypted command records and append-only encrypted workflow revisions. Runtime privileges and readiness include both tables. The experimental BFF-only isolated-development routes are `POST/GET /api/v1/sites/:tenantId/:siteId/recovery`, `GET /recovery/:id`, `POST /recovery/:id/retry`, and `GET/POST /recovery/workflow` under the same site prefix. A retry chooses its route from a server allowlist, invokes the normal authenticated business handler with the saved idempotency key, and marks the record resolved only after that handler succeeds and the completed receipt exists. The workflow API uses optimistic revisions and preserves old revisions. Registration and completion audit records contain identifiers and type, not the request payload. The backend requires a separately provisioned base64 32-byte `RECOVERY_ENCRYPTION_KEY` and `RECOVERY_KEY_VERSION`; losing the key makes the encrypted data unrecoverable. Configuration rejects recovery unless BFF and explicit isolated-development mode are enabled.

This remains **NO-GO**: the premium UI and the older integration page have not been moved to these APIs; legacy browser plaintext has not been migrated or cleaned. The new frontend remote-journal module is not wired into any application screen. Current data is still exposed in shared browser storage. A keyring for accessing records across key rotations and a verified deployment secret-management/backup procedure remain open. A same-tab two-user test against the finished workflow and complete source/packaged regression suites are mandatory before completion. The legacy pre-upgrade plaintext limitation above still applies.

The `server-pending-commands.js` browser adapter is a tested but unbundled prototype; it stores only scoped opaque IDs and command fingerprints in browser storage, and sends payloads to the encrypted server API. It is not wired into the premium UI or older integration page. The remote workflow client, legacy migration, real multi-user same-tab pending-command acceptance, and complete frontend/packaged regressions remain unfinished. Do not use this as a completed confidentiality fix.

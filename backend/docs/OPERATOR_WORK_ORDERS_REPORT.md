# Operator's assigned work orders — development integration

Baseline `027cf29bb5ee5ad19095309cde81dd733c1a423b`. The isolated-development API now offers self-only work-order discovery; see API_CONTRACT.md for its request, fields and pagination. It uses the verified identity, active operator membership, scope transaction, forced RLS and the existing restricted runtime grants. A manager without an active operator role gets 403; a manager who is also an operator sees only their own assignments. No migration, grant extension, MES write, frontend or production activation was added. Production and drawing authorization gates are unchanged.

Fixture creation/migration uses privileged setup and a separate schema owner; API/RLS queries use a restricted NOINHERIT, NOBYPASSRLS runtime. [Complete TAP](evidence/operator-work-orders-postgresql16.tap). Existing RLS, concurrency and backup/restore regressions also ran. An initial full run failed backup/restore because local pg_dump 14 could not dump PostgreSQL 16; the verified rerun used PostgreSQL 16 pg_dump and pg_restore inside the isolated database container.

Docker Compose: PostgreSQL 16 healthy, separate migration and runtime roles, migrate and provision exited successfully, API started; `/health/ready` returned 200 and an unauthenticated request to the new API returned 401. The first image build failed because docker-credential-desktop was absent from PATH; rerunning with Docker Desktop's CLI directory succeeded. All test credentials and records were fictional. Existing Docker volumes and user databases were not deleted or reset.

GO for the narrowly scoped frontend development dependency; NO-GO for production use or deployment. This read is not a write authorization, and RLS does not protect against arbitrary SQL in a compromised runtime process that forges transaction context.

# Inventory integration: current dependency analysis

Status: implementation not completed; no inventory endpoint or migration has been enabled by this analysis. Production and development acceptance remain NO-GO.

The current `lots` primary identity is scoped to `(tenant_id, site_id, order_id, id)` and every lot must reference an order. `material_receipts` is likewise order-bound, its document reference is unique per site, and its piece quantity is a positive safe integer. The existing development-only fictional receipt path creates an order-bound lot and caps its receipts against order quantity. It is not a warehouse receipt and cannot represent reusable stock across orders.

B03C first-operation `physical-receipts` requires an active reservation, verifies order-bound lot receipt and allocation totals, checks work-order capacity and then appends a physical ledger receipt. B04A production accepts only reconciled physically received inputs; it locks and validates assignments, checks operator identity and active drawing acknowledgement, and creates output provenance separately. Warehouse stock must never be made available to production merely by a planning reservation or by historic production counts.

A safe integration requires a separate tenant/site-scoped material master, hierarchy, warehouse-lot and append-only location movement ledger. Each warehouse-to-order pick must atomically: lock the relevant warehouse lot/location and order/work order in a consistent documented order; calculate current available stock from movements; reject insufficient quantity; create an order-bound material lot with an immutable link to the warehouse lot and pick; create the existing required material receipt and reservation with trustworthy supplier/document provenance; append the physical receipt only if the warehouse pick represents an actual physical handover; append the warehouse debit; write audit and idempotency receipt; and commit or roll back everything together. An allocation without physical handover must not append receipt. The design must avoid reusing the same unique supplier document reference on multiple order-bound pick records, and must not present the internal handover record as a new supplier receipt.

Concurrent moves, picks and scrap must serialize on the same stock-balance lock or an equivalent deterministic locking protocol, including opposite-direction location moves. Read projections must use only authoritative location movements and check safe-integer piece quantities; conversions for other units require an independently specified exact conversion policy and must not fabricate piece counts. Forced RLS, runtime grants, readiness and migration tests must cover each new table. Read and mutation capabilities must be checked using current server-side memberships under transaction locks.

The authenticated frontend uses the BFF-only encrypted recovery catalog: new mutation types must be explicitly allowlisted and resource authorization rechecked on registration, read and retry. Adding a route alone is insufficient. The current premium job material panel is explicitly fictional and calls the development-only fictional endpoints; it must remain distinct from the new inventory screens and never act as fallback. Existing local demo data and old order-bound lots must remain untouched; no automatic reinterpretation of historical lots is safe.

Still required: reviewed PostgreSQL migrations and grants; transaction-safe receipt/move/pick/scrap services and projections; production handover provenance; recovery catalog integration; premium UI; real restricted-role PostgreSQL 16 and Keycloak end-to-end, concurrency, audit rollback, tenant/site isolation and packaged/source browser regression evidence. No tests or migration results are claimed by this document.

# B04B-1B — output-lot provenance foundation

Migration 009 introduces an event-specific `production_output_lots` identity, separate from the input `lots` record. Event-specific identities are the smallest unit supported by B04A's single-input-lot production event; aggregation would require additional compatibility and genealogy rules. Two composite foreign keys tie each immutable row to the consume and output ledger rows, with tenant, site, order, work order, production event and input lot in common. Production ledger event constraints enforce the event quantity and actor of those ledger entries. The new identity is generated by the server, never accepted from the production request. RLS is forced; runtime has SELECT and development-only INSERT, no UPDATE or DELETE. The migration does not create reservations or enable a downstream flow.

For supported `good` and `pending` production, event, both physical accounting entries, output identity, audit and idempotency receipt commit in the same locked transaction. Quality decisions preserve the historical `lotId` meaning (input lot) and new decisions attach the event's server-derived output identity through a composite foreign key. An optional supplied output identity is checked, not trusted. The summary shows the distinct output identity and explicitly keeps reservation unavailable. Old production events and decisions are not rewritten; their output identity is null, provenance is `historical_unreconciled`, and no reservation capability is exposed. Old unrecorded provenance is never inferred.

This is a provenance foundation, not approved or physical downstream inventory. Full B04B-1B reservation ledger and ordered release/re-reservation, downstream planning and physical receipt remain unimplemented. B04A completion remains blocked by historical pending output even after quality decisions; B04B-1C is separate. Evidence references remain actor-provided strings and are not independently verified. Drawings still fail closed. As documented in B03A, a compromised runtime able to execute arbitrary SQL can forge transaction scope; RLS is defense in depth rather than a security boundary against that threat. Production write routes remain disabled outside isolated development.

## Validation

Real PostgreSQL 16 using restricted runtime credentials: **91/91 tests passed**, no skips. [Full TAP](evidence/b04b1b-output-lot-postgresql16.tap). Tests cover distinct input/output IDs, genealogy, quality attachment, forged ID rejection, duplicate command retry, concurrent production, audit rollback, immutable history, legacy decision readability without backfill, restricted runtime privileges, RLS and readiness. Migration recovery tests upgrade existing fictional schema to 009 and verify failed 010 rollback and backup/restore. Initial forged-row test encountered the correct unique constraint before the intended foreign-key check; the fixture was corrected to use a distinct fake event and the full test suite rerun.

[Compose smoke](evidence/b04b1b-output-lot-compose.txt) uses a separate fictional tmpfs database, separate migration and restricted runtime logins, and checks migration/provisioning/startup, readiness and unauthenticated rejection. It does not verify a live OIDC provider.

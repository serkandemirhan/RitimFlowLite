## Isolation and deployment sequence

Tests used uniquely named Compose projects, synthetic credentials and data, and PostgreSQL data on container tmpfs. The bootstrap SQL was a read-only bind mount. Database and API host ports were loopback-only; no preexisting Docker containers, volumes or databases were deleted/reset. The fixture first ran with password-authenticated distinct owner and runtime roles. For the automated integration suite only, the fixture's `pg_hba.conf` was temporarily changed to trust connections in this isolated loopback-bound test instance so the suite could create and connect using random non-superuser LOGIN roles. This is a test convenience, **not** a deployment recommendation; production must require authentication and secure network controls.

Compose now waits for DB health, executes migration as the migration owner, runs `security/provision-runtime.js` as that owner, and starts the API only after provisioning succeeds. The API includes a health check. The fixture's migration and provisioning containers exited 0; DB and API became healthy. [Compose startup evidence](evidence/b03a1-compose-startup.log). Roles and schema still must be pre-provisioned; Compose does not bootstrap production identities automatically.

Two independent negative fixtures exercised orchestration: a runtime login with INHERIT was rejected by provisioning, leaving API in Created state ([log](evidence/b03a1-provision-rejection.log)); a deliberately incorrect prior migration checksum caused migration to exit 1, leaving provision/API unstarted ([log](evidence/b03a1-migration-rejection.log)). All fixtures were fictional and isolated.

## Readiness and permission tests

Migration 004 exposes migration version/checksum rows through a search-path-hardened SECURITY DEFINER function; direct migration-table rights remain unavailable to runtime. `/health/ready` checks installed migration versions/checksums, runtime role safety, required schema/table/function privileges and forced RLS flags across 22 scoped tables. It returns 503 if checks fail. Against the running Compose API, revoking runtime INSERT on idempotency yielded 503 and restoring it yielded 200; deleting the fictional 004 migration record yielded 503 and restoring it yielded 200. The automated restricted-role test also checks changed migration checksum. Readiness is not proof of identity-provider reachability, business rules, every possible RLS policy or security against arbitrary runtime SQL.

Separate migration/schema-owner and real restricted runtime logins were verified. The suite checks two tenants and site scopes, no-scope failure, RLS read and idempotency write isolation, forbidden privilege escalation, pooled connection reuse, rollback, concurrent membership revocation, temp-table search-path injection and role/schema/migration privilege denial. A deliberately compromised runtime can still forge mutable transaction context and read another tenant: the negative test succeeds as **evidence of a remaining threat**, not a passed security guarantee. Database-layer protection against a compromised runtime needs an independently trusted identity broker or verified cryptographic context and separate review.

## Tests, migration and recovery

`npm test` against PostgreSQL 16.10: **43/43 passed, zero failed or skipped**. [TAP evidence](evidence/b03a1-postgresql16.tap). B01/B02 security and domain foundations and the B03A restricted-role suite were included. Fixture setup/schema creation uses a privileged bootstrap account; the migration uses a separate non-superuser owner and application/security checks use a separate restricted LOGIN. Test API identity adapter is fictional; B02 signature tests exercise real cryptographic JWT verification.

The migration recovery test upgrades an existing fictional 001/002 database to 003/004, checks records unchanged, injects a failing 005 migration and confirms transaction rollback, then uses **PostgreSQL 16 pg_dump/pg_restore from the container** to restore a synthetic backup into a separate fictional database. It validates order data, migration versions and RLS flags. The test dump SHA-256 is recorded in TAP; it was a temporary fixture, not a user backup. The preceding PostgreSQL 14 recovery procedure remains in the [historical report](B03A1_DEPLOYMENT_VERIFICATION.md). Actual deployment backup/restore, role regrant, recovery point and rollback need their own verified operational exercise.

The built image runs as `node` and `/app/.env` and `/app/.env.local` were absent in the running API container. Image inspection did not constitute a comprehensive secret scan. Compose injects passwords as container environment variables, visible to Docker administrators; use appropriate target secret management and TLS. Docker image digests, live provider interoperability, deployment permissions, cloud/on-prem differences, PostgreSQL policy/grant reviews, monitoring and backup drills must be reviewed on each actual target. Do not use fixture trust authentication outside this isolated test.

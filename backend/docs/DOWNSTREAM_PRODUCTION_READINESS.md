# Downstream production readiness — isolated development

The first and immediately following internal operations are supported; later and external operations remain unsupported. No schema migration is required: B04B-2 `operation_receipts` is the authoritative input for operation 20, and existing immutable `production_ledger` and `production_output_lots` retain production and genealogy. The input lot must belong to the receiving work order; receipts reference dispatch, reservation, approved source output and source input genealogy through scoped foreign keys. The order lock serializes receipts, production, quality and reservations. Production writes, output lot, idempotency and audit commit atomically.

B04A first-operation work consumes only `physical_ledger` receipts; the next operation consumes only its own `operation_receipts`. Mixed inappropriate input history is rejected. Reserved and in-transit quantities are not usable input. For each input lot, remaining = physical receipt less production consumption; overdraw, orphan consumption and production without paired output movements fail closed. The input endpoint reports received and remaining physical amounts separately. Historical production totals remain separate from physical input balances. Each good or pending event receives its own output lot. Recording production does not approve it; downstream quality decisions use the existing evidence, authorization and locking contract.

Receipt and dispatch to an already started or paused destination are supported under the same order lock, allowing partial input to be processed while the rest is in transit. Completion requires the complete planned physical input, no remaining usable input, no inbound movements, no unresolved quality and no open rework. Start, pause, resume, completion and results retain operator membership, assignment and machine checks. Pause remains available when a drawing appears, but start/resume/results/complete and quality decisions fail closed on any drawing revision.

The minimum future drawing acknowledgement contract must bind a server-verified actor to tenant, site, work order and immutable revision/content hash, record timestamp and evidence with audit/idempotency, require the current applicable revision at execution time and handle revision changes under the same transaction lock. No acknowledgement or approval is inferred here. Rework execution, third and later operation planning/transfer, outsourcing and production deployment remain unsupported. Security remains subject to the documented arbitrary-SQL/runtime compromise limitation.

## Verification

The PostgreSQL 16 restricted-runtime scenario creates 20 pending units, classifies 12 approved/3 rejected/5 rework, reserves and dispatches 8, receives 5, then checks start, capacity, genealogy, concurrent results, idempotent retry, audit rollback, pause/resume, revoked assignment, later partial receipts, quality decisions and completion. A second destination verifies reserved-only and in-transit-only stock cannot start production, and verifies the drawing gate after physical receipt. Cross-site and forged input references are rejected. Existing B01–B04B-2 regressions and migration/backup checks run in the full suite. Evidence: `evidence/downstream-postgresql16.tap` and `evidence/downstream-compose-smoke.txt`. Privileged setup/migration roles create fictional fixtures and perform backup/restore; application calls use the restricted runtime. Node 22 and PostgreSQL 16 client tools are required.

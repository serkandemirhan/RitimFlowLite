# Real OIDC development integration

Status: **development NO-GO for shared-browser confidentiality; production NO-GO.** This work is uncommitted until all requested acceptance gates pass. Backend and frontend remain in their existing separate worktrees.

The development BFF uses Authorization Code + PKCE S256, state and nonce; validates the ID token against discovered issuer/JWKS and validates the access token with the server's existing verifier; matches subjects; and stores tokens only in process memory. The browser receives a random HttpOnly, SameSite=Lax, bounded session cookie (Secure on HTTPS). Cookie-based mutations and logout require the configured origin. Sessions have an absolute lifetime bounded by both token expirations, with no refresh-token persistence or automatic renewal. Restart loses all sessions. Logout removes the application session and invokes the IdP logout endpoint; it does not guarantee immediate revocation of an independently held bearer token. Keycloak's `JWT` access-token type is permitted only in the explicit provider-compatible configuration and still requires a signed bearer token, audience and issuer; an ID-shaped token is rejected.

Identity is established from verified issuer/subject and authorization comes from current PostgreSQL memberships, capabilities and RLS. API mode has no localStorage fallback. Pending command identity remains actor/tenant/site scoped; the existing demo remains separate. The manual-token UI is restricted to explicitly selected development tooling when the server confirms isolated-development mode. TLS is mandatory for the IdP; plain HTTP app origins are permitted only for loopback development. The provider and application must use distinct audiences. Production still needs a reviewed distributed session/revocation design, TLS, secret management, hardened IdP, secure network configuration, operational rotation and monitoring, plus the previously documented compromised-runtime limitation.

The resumable command journal and wizard metadata live in browser sessionStorage and are filtered by verified actor/tenant/site in the UI. This is not an isolation boundary against another person using browser developer tools in the same browser session; production needs a reviewed server-side recovery store or an equivalent stronger design. Legacy single-key wizard state remains untouched for its owner; new workflows use scoped keys.

**Release blocker:** the scoped journal still stores request bodies and order workflow fields as plaintext in shared-tab sessionStorage. A later authenticated user can inspect those values using browser developer tools even though the application UI correctly filters them. A server-authorized recovery store or equivalent design must preserve uncertain command identity while preventing cross-user inspection; until implemented and tested, the explicit cross-user confidentiality acceptance is not complete. No completion commits were made. Local fake-fixture setup and OIDC-enabled container-to-container networking also need dedicated deployment validation.

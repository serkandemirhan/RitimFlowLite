# OIDC secure pending-command recovery

Status: **NO-GO for shared profiles containing unmigrated legacy plaintext; production NO-GO**. This implementation is restricted to explicitly configured isolated development.

New pending command bodies and multi-step order wizard state are sent to the authenticated backend and encrypted in PostgreSQL. Browser storage holds only opaque scoped command identifiers. The server binds recovery to the verified actor, tenant and site, rechecks current authorization and the resource, and replays only a server-allowlisted command with the original durable idempotency key. Resolved commands remain available until explicitly acknowledged. Deterministic rejection is serialized with the business command so a rejected identity cannot subsequently create a mutation. Wizard steps are stored as encrypted append-only revisions; the three order steps are not presented as a single database transaction.

Legacy browser records are migrated only after the original actor authenticates and explicitly requests migration. The server must durably accept the same command identity before source plaintext is removed. Foreign or unrecognized records are retained and the workspace is blocked. Historical plaintext was already readable before the upgrade and cannot be made unreadable retroactively. Old-version tabs or other profiles must independently complete owner-assisted migration or an explicitly approved secure reconciliation/cleanup; merely installing this version does not meet the shared-profile confidentiality requirement for those records.

Backend migrations 015–018 add forced-RLS encrypted command and workflow records, rejection handling and acknowledgement. The site-scoped API provides register/list/get/retry/acknowledge and workflow read/save. A separately managed AES-256-GCM key is required; losing it prevents recovery. A multi-version keyring, key rotation/backup operations, audited retention and safe expiry cleanup remain outstanding. Current expiry metadata does not automatically delete unresolved or acknowledged records.

Current verification: PostgreSQL 16 backend regression **124/124** with the restricted runtime role; focused frontend recovery unit tests **13/13**; a real Keycloak/Fastify/PostgreSQL browser scenario **1/1**, including a lost response, same-tab identity change, explicit legacy migration and server restart. Source premium I02, production/quality and two-operation integration scenarios each passed once; source Sprint 2 responsive checks **7/7** passed. The complete CI and packaged integration runs must be reported separately after they finish. Captured TAP output is in `secure-recovery-evidence/`; a prior failed restart attempt is retained there as well.

The same three integration scenarios and seven Sprint 2 responsive checks also passed against the generated package. The first complete CI attempt stopped in P0 integrity with 9/11 passing: two 7-second page-load/readiness timeouts occurred while other browser tests were executing. The recorded application error count was zero. The failing package subsequently passed **11/11** in isolation. This suggests resource contention but does not prove its cause. A complete single `npm run test:ci` rerun without concurrent browser tests passed: 292 domain, 13 recovery, 12 packaging, 110 source browser, 110 packaged browser, and 32 source plus 32 packaged isolation/Sprint checks; the package smoke loaded all 45 assets without application errors. The earlier OIDC restart failure was caused by the test advancing its clock and expiring sessions before registration; the test sequence was corrected and the real-provider run passed.

Dockerized PostgreSQL 16 and Keycloak were used by the real-provider test with the Fastify API running on the host. This is not proof of API-to-Keycloak connectivity from inside the API Compose container; that deployment-specific smoke remains pending. The local legacy coexistence test uses an archived local artifact and does not prove the currently published Pages version.

The current implementation uses real Keycloak authorization code and BFF session identity, PostgreSQL membership checks, restricted runtime privileges and normal business idempotency. It does not claim protection against arbitrary SQL in a compromised application process or malicious same-origin scripts. Production deployment, live credentials and actual mobile acceptance remain outside this verification.

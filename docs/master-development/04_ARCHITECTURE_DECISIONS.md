- E: Yetkili iş olayları, sürümlü ana veriler, çizim dosyaları/özetleri ve kaynak denetim ilişkileri öneriliyor. Şifreler, oturumlar, anahtarlar ve tarayıcı bekleyen komutları kopyalanmayacak.

| Decision | Alternatives and consequences | Recommendation requiring approval |
|---|---|---|
| A: offline identity | Local identity service: supports first login and long outages but adds credential/key/patch operations. Time-limited cached cloud authorization: simpler but cannot grant first offline login and must expire. Unlimited cache: simple but leaves revoked accounts authorized indefinitely. Cloud password changes cannot automatically reach an isolated server. | Local identity service with explicit cloud-to-local identity mapping; separately scoped local credentials, audited local admin provisioning, configurable offline authorization lease and emergency revocation. Agree maximum outage lease and first-login/revocation policy before implementation. |
| B: conflicts and authority | Single writer for each site/resource: limits concurrent flexibility but makes physical quantities safer and maintenance simpler. Concurrent writes with reservation/escrow and reconciliation: more flexibility, substantially more complexity and cost. Last-write-wins loses manufacturing facts. | Site owns physical stock/production commands; immutable identified events synchronize, mutable master records use versions and visible conflicts. Cloud requests to site-owned resources wait for authoritative acceptance. Confirm whether cloud must mutate the same stock during site outage. |
| C: deployment | Workshop Fastify/PostgreSQL plus persistent cloud API: preserves domain but adds server operations. Serverless adaptation: different connection/lifecycle constraints and more engineering. Cloud-only API cannot meet outage requirements. | One local application server per workshop; persistent managed Fastify cloud service, Supabase DB/Auth and Vercel frontend. Provider, cost and local TLS/identity operation remain undecided. |
| D: tenant ownership | One installation per tenant is simpler but restricts growth. Multiple sites/installations support growth but require scoped authority, enrollment and duplicate-installation protection. | Support tenant with multiple sites, one authoritative writer installation per site initially; cloud-issued installation UUID and keys, controlled replacement/recovery. Approve multiple installations and enrollment ownership explicitly. |
| E: sync boundary | All tables/passwords/pending commands: superficially easy but breaks trust and recovery semantics. Domain envelopes with selected categories: more mapping work, clearer authorization and compatibility. Files need independent integrity/availability handling. | Versioned domain events/master versions, drawing metadata plus hashed file transfer, provenance-preserving audit references. Credentials, sessions and encrypted browser pending commands stay local; minimal identity/membership metadata follows an approved lease policy. Approve each category before implementation. |
| F: device offline | Internet outage with working LAN/server: shared transactions and simpler support. Each device disconnected from LAN: additional local storage, identity, command queue, conflicts and lost-device exposure. | First scope is internet outage with LAN/local server available. Disconnected-phone/laptop mutation is a separate explicit scope decision. |
| G: rollout / recovery | Replace/import customer data in one step: lower effort but high rollback risk. Pilot with backups, dry-run mapping, checkpoints and reconciliation: more effort, controlled recovery. Restoring a synced database can replay already accepted events unless origin identities survive. | Dedicated fictional staging first; read-only customer import analysis, explicit approved migration window, verified backup/restore, resumable quarantined replay and reconciliation before reopening writes. No customer data mutation or production rollout in this program without separate authorization. |

No policy in this table is an implementation default. Approval should identify A–G and any changes, including lease duration, site/cloud writing authority, hosting provider, installation count, sync categories, device scope and migration responsibility.

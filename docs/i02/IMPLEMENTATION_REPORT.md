# I02 — premium API development mode

Branch `integration/i01-frontend-backend`; local checkpoint `5d982ed` preserves the I01 and Sprint 0/1 snapshot. API mode is selected at `/?mode=api`, and the existing demo offers a localhost-only link to it. The application uses the existing premium wizard, modal accessibility behavior and design styles on the same `index.html` entry point. API mode is explicitly restricted to localhost and never opens the demo storage session. Unsupported production, quality, transfers, outsourcing, shipment, drawings and machine assignment are not offered as API mutations. The original local demo retains its own screens and persistence.

## Screens and contract

- Orders: `GET /api/v1/sites/{tenant}/{site}/orders`, in-memory search over the returned list (server currently caps at 200); order card shipment quantity is the server's `netShipped`.
- Order detail and ordered route: `GET .../orders/{orderId}`. Work order lists and detail use `GET .../orders/{orderId}/work-orders`; work-order planned quantity and recorded historical output remain separate from order quantity. Physical received may be unknown.
- Planning: `GET .../orders/{orderId}/operations/{operationId}/availability` and `POST .../orders/{orderId}/work-orders`; only the server-supported first internal operation is enabled. The server determines available quantity and validates all writes.
- Wizard: `POST .../orders`, then `POST .../orders/{orderId}/route`, then optionally `POST .../orders/{orderId}/work-orders`. These are separate transactions. Order, route and plan show waiting, unknown, failed, committed or skipped. Confirmed failed stages can be corrected; unknown stages remain locked until retried with the same command key. Before a later action the order/route and, for planning, the work-order list are re-read. If saving a successful response to the workflow journal fails, the idempotency receipt stays pending for safe replay. The workflow and command journal are actor/site scoped, sessionStorage-based, and contain fictional order data but no access token. They survive reload in the same browser tab, not tab destruction or storage eviction.

Manual short-lived access tokens are explicitly development tooling and remain in memory. Server-verified session and capabilities gate controls; the API still rechecks authorization in its transaction. `auth-provider.js` only defines a future provider interface. No live OIDC login is implemented or claimed. API connection failures do not fall back to localStorage. The development proxy binds loopback, proxies to loopback Fastify, and is not a production ingress. Legacy local commands are disabled in API mode.

## Verification and boundaries

See final test report for exact totals and current run status. Source and packaged premium API browser scenarios exercise fictional PostgreSQL 16 via real Fastify and verified RSA-signed fictional JWTs with simulated JWKS. They cover wizard success and response loss, reload and same-key retry, optional first plan, 5+5 and overplan rejection, search, two browser sessions, operator controls, cross-tenant/site denial, isolated demo key, work-order detail, 320/360/390/430 CSS widths and keyboard focus/Escape. Concurrent overplanning was tested against the same backend in the I01 browser integration suite. Automated desktop Chrome viewport checks do not replace physical mobile Safari/Android acceptance.

The PDF `ERR_ABORTED` investigation is separate. The [previous Ubuntu GitHub Actions run](https://github.com/serkandemirhan/RitimFlowLite/actions/runs/40648159648) passed all 11 P1 cases but failed the application-error gate: its retained `browser-results.json` identifies the aborted request as the actual loopback `teknikResim.pdf` URL in the P1-01/16 drawing test. The test closes the drawing modal after checking zoom; this is consistent with a cancellation during loading, but timing was not conclusively established. In contrast, macOS telemetry recorded an abort from Chrome’s PDF extension. The pre-existing harness excludes extension-URL failures, not all network failures. No request failure was newly suppressed. The changed candidate was not run on GitHub Linux, so Linux verification remains open. Hosted production, real OIDC/provider interoperability, token renewal, server-side defenses against an arbitrarily compromised runtime, external operations and multi-device production activation remain outside this development slice. No real data was used or migrated.

## Local development

Start the separately configured B03B Fastify service with an isolated fictional PostgreSQL database and verified development identity provider. Then run `node integration/dev-server.cjs` using Node 22 and open `http://127.0.0.1:4178/?mode=api`; `I01_API_PORT` and `I01_WEB_PORT` select loopback ports. The default `http://127.0.0.1:4178/` remains the independent local demo. Do not use the proxy for production or expose database credentials to the browser.

# Customer shipping integration — development verification

The isolated-development API uses migration 020. Shipping orders and immutable allocation, dispatch and delivery events reference tenant/site/order, an event-specific production output lot and the original command receipt. Per-order locking serializes quality, reservations and shipping. A lot is eligible only for a completed final internal operation on a supported one- or two-operation internal route; quality approval and trusted output genealogy are mandatory. Allocation subtracts outstanding downstream reservations and previous allocations; dispatch and delivery are separate partial events. Customer returns, allocation cancellation and external routes are unsupported. Order progress includes dispatches; delivery is explicitly recorded rather than inferred.

The premium API mode uses server-authoritative balances and encrypted server recovery for all shipping writes. Fictional demo mode remains separate. The new endpoints are development-only and are not approved for production.

Initial evidence includes PostgreSQL 16 restricted-runtime regression, fictional Keycloak/Compose source and packaged scenarios, 320–1440 CSS-pixel layout checks and real two-operation production. Initial CI caught a PDF request `ERR_ABORTED`; its evidence is retained and the P1 suite was repeated without suppressing errors. Source and packaged two-operation Keycloak scenarios and the complete frontend suite passed.

Verified against the isolated PostgreSQL 16 fixture: the backend full regression reported 133/133; the later focused suite reported 16/16 including competing allocation/dispatch, replay, cross-tenant/role denial, audit rollback and missing shipping grants. A fictional 100-unit order with 60 approved output units yielded allocation 40, dispatch 40, delivery 30, in transit 10 and available 20. The real Chrome/Keycloak/Fastify source and packaged scenarios also traversed warehouse receipt, pick, two internal operations, quality decisions and shipping, with a deliberately lost allocation response followed by same-key recovery; it verifies the database genealogy back to the warehouse lot. Compose readiness was 200 and anonymous shipping access 401. The 320–1440 viewport checks do not replace real iOS/Android acceptance.

Remaining limits include customer returns, allocation cancellation, outsourced/third operations and production security/deployment gates. The ready list currently retrieves per-order server projections and is limited by the existing 200-order API; pagination and scale testing remain necessary. Production activation remains NO-GO.

Shipping order states are derived by the API from event totals and shown in the premium screen. The verified partial-dispatch scenario uses 20 approved final units, 15 allocated, 10 dispatched and 7 delivered: five allocated units await dispatch, three are in transit and five remain available for allocation.

During one interim Compose startup, a readiness request arrived before the API listener and received an empty response; after startup the same isolated service returned 200. Only temporary API containers created by this task were stopped; no existing volume or database was removed or reset.

Rollback constraint: an older backend does not read `shipping_events` in order progress or enforce its allocations. Do not re-enable older writers against a database containing shipping events. A safe rollback requires isolating writers and a separately reviewed data-compatibility/reconciliation plan; no rollback migration or automatic merge is provided.

Fictional isolated test schemas and task-created Compose containers may remain locally, including artifacts from interrupted test attempts. They were not removed or reset; no existing user database or Docker volume was deleted.

Reproduction requires a disposable PostgreSQL 16 fixture, restricted runtime provisioning, the fictional Keycloak realm and local test-only secrets. Run `npm test` from `backend/` with `TEST_DATABASE_URL` pointing at the disposable setup database. Run `npm run test:ci` in the frontend with a Playwright-managed Chromium or `AUDIT_CHROME` set to the local Chrome binary. Run `node --test tests/shipping-oidc-browser.cjs` with `SHIPPING_TWO_OPERATION=1`, `OIDC_FIXTURE_DIR`, `OIDC_TEST_PASSWORD`, `TEST_DATABASE_URL`, `RITIM_BACKEND_DIR`, `I01_API_PORT` and `AUDIT_CHROME` configured for the isolated environment; set `RITIM_APP_ROOT` to the verified distribution root for the packaged repeat. Never use real production records or secrets for these fixtures.

The development screen shows technical lot and shipment identifiers; when several shipment orders exist, allocation/dispatch choices are not automatically filtered by the selected shipment order. The server checks the relationship and rejects mismatches. More descriptive labels and contextual filtering remain usability work before broader rollout.

Delivery confirmation records an authenticated authorized user's explicit report and its audit trail; it is not independent customer identity verification, a signed proof of delivery or a carrier integration.
Several intermediate CI runs were deliberately interrupted when their source snapshot was superseded; their partial results are not counted as completed full-suite runs.
The development shipping history is currently returned without pagination; bounded pagination and load testing are required before operating on large production histories.

Final `npm run test:ci`: 292/292 domain, 12/12 recovery, 12/12 packaging, 1/1 smoke, 110/110 source browser, 110/110 packaged browser and 32/32 isolation checks for each target. The final run reported zero unexpected browser application errors. Verified public-asset digest: `8e15d757ce03afa8edb689aadf89479ec621e02b7930cac25691c110b39df14e`. These are local results; GitHub Actions was not run or represented as passed.

Decision: development GO for the explicitly supported isolated fictional workflows; production activation NO-GO pending the security, operational, device and usability limits above.

# Ritim Flow Lite — UX/UI and functional completeness audit

Audit date: 26 October 2026 (Europe/Istanbul). Baseline commit: `a28d562`. Scope: the entire tracked application, both HTML entry points, all five JavaScript and five CSS extensions, README, PDF reference, placeholder test file, and deployment workflow. No separate PRD or AGENTS.md was found; the supplied audit request is the acceptance specification. This audit changes documentation and test artifacts only. No application changes, push, or deployment were performed.

## Assessment

**Partial manufacturing demo; incomplete end-to-end MES workflows and unsafe as a source of physical inventory truth.** The operator extension implements useful quantity validation, inspection, rework results, handover, and closure restrictions. The logistics extension supports bounded partial receipts, allocations, dispatches, returns, final approvals, shipments, and customer returns in its own ledger. These are actual executable features, not just buttons.

However, the dashboard and order cards use fixed stock snapshots; the original shipment records and UX-06 shipment records remain separate; work orders cannot select a downstream operation; physical stock has no transfer/lot/location model; and final release can bypass intermediate operations. No screen earns “Complete” against the full requested scope. This is a scope assessment, not a fabricated percentage of implementation effort.

Browser evidence was collected with standalone Playwright controlling installed Chrome after the in-app browser reported no available browser. Desktop 1440×1000 and mobile 390×1000 / 360×1000 were exercised. Browser widths are emulations, not real workshop-device tests. See [executed results](UX_E2E_TEST_RESULTS.md) and [raw evidence](audit/evidence/results.json). The live HTML, PDF and all ten extension assets returned HTTP 200 and matched local SHA-256 hashes: [comparison manifest](audit/evidence/live-source-comparison.json). Functional mutations were run locally with isolated, fictional fixtures, not against an existing user profile.

## Top ten problems

1. **P0 — Multiple incompatible quantity truths.** `shipmentSummary()` reads `sampleStageStocks`, legacy shipping reads `state.shipments`, UX-06 reads `state.ux06`. A newly shipped 20/20 order still reports 0% in order detail (T14). Initial DEMO-SIP-005 displays 100 shipped in snapshot versus 60 legacy shipped versus 0 UX-06 shipped.
2. **P0 — Routing does not gate final release.** On `İmalat → Tesviye`, 10 good from operation 0 can become final approved stock (T15). The external path likewise recognizes any route containing Kaplama rather than its actual sequence.
3. **P0 — Legacy shipment path bypasses final QA.** T17 called retained `openShip()` to open the old form and clicked save: 10 shipped, zero final release, job marked shipped. This is a programmatically reachable legacy command, not a claim that its disabled normal button was clickable. The separate sales page also retains the old rules.
4. **P0 — No physical transfer model.** Dispatch leaves source good/received counters unchanged with no outbound quantity dimension (T16); those counters could represent historical output, but the app cannot derive current location from them. Verified-good-minus-dispatch does prevent repeating the same UX-06 dispatch; the test does **not** prove repeat dispatch is accepted.
5. **P0 — Additional-job planning cannot select operation/quantity.** T05 creates another op-0 job with no plannedQty. Each falls back to the entire order quantity; cumulative planning limits and transfer reservations do not exist.
6. **P0 — Reconciliation gives false reassurance.** Overplan 200 against a 150 job plus an allocation to a missing job produce no warning (T18). These were intentionally injected invalid fixtures, not records claimed to be produced by the normal allocation form. The “read-only” audit creates empty ledgers in memory (T19).
7. **P0 — Persistence/recovery is not safe.** Quota failure keeps a material receipt in memory while storage is unchanged (T25). Valid JSON with `jobs:null` crashes `home()` without a recovery view (T26). Multiple tabs can overwrite whole snapshots; concurrency was reviewed, not stress-tested.
8. **P1 — Work-order navigation can lose or change the target.** Unassigned job opens CNC-01's job (T20). Drawing uses `chosenJob` for its order, overwriting the selected work order; the next detail-tab render cannot find the job (T32).
9. **P1 — Operational navigation is incomplete.** KPI count/list mismatches (T02); back clears filters (T03); no order-context logistics links, My Jobs, QC backlog or return-disposition flow. Mobile lacks UX-07 and history navigation entries (T21).
10. **P1 — Visible layout and interaction defects.** Missing dashboard selectors leave default browser buttons and collapsed label spacing. Audit overflows both mobile widths (T01). Technical drawing Enter activation fails (T28); many secondary controls are under 44px tall. See screenshots, not just CSS inference.

## Business-rule analysis and acceptance quantities

The requested example executes correctly **inside UX-05**:

| Dimension | Expected | Observed (T06) |
|---|---:|---:|
| Order / planned work order | 250 / 150 | 250 / 150 |
| Physically received | 100 | 100 |
| Good / production scrap / setup scrap | 60 / 3 / 0 | 60 / 3 / 0 |
| Pending inspection / pending rework | 12 / 0 | 12 / 0 |
| Not yet processed | 25 | 25 |
| Planned but not physically started | 50 | 50 |

`100 = 60 + 3 + 0 + 12 + 0 + 25`; `150 = 100 + 50`. Equivalent production entry ran at 390px and 360px. This proves local classification arithmetic, not the full transfer acceptance criterion. Moving the 25 requires a missing controlled physical transfer; moving the 50 requires missing plan/reservation reassignment. Neither can be treated as simply “75 available.”

The current model separates received, several quality counters and one planning quantity, but not physical location, lot identity, downstream acceptance, reservations that can be released, or shipment lineage. Good remains cumulative in jobs; logistics sums independent arrays. There is no unique batch/movement identity linking an accepted input to its output and destination. Material receipts are capped at order quantity and allocations remain cumulative forever, so scrap replacement/compensation and multi-operation reuse cannot be modelled correctly.

External dispatch is distinct from customer shipment in UX-06 and does not directly increment its `net`. Customer returns decrease net and do not increase ready stock, a useful safe default. Yet net does not drive overall order completion, and return dispositions/reversals are absent. Conditional release is not implemented: no UI enables it by default, but there is also no explicit policy/authorization model to enforce it. Final QA restrictions are incomplete, as T15/T17 demonstrate.

Existing guards worth preserving: allocation ≤ free material and per-job plan; new physical receipt ≤ allocation and plan; result entry ≤ unprocessed; manager UI checks for quality decisions; inspection/rework bucket conservation; work-order closure with no pending/rework/unprocessed/unstarted remainder; external return ≤ dispatch remainder; unique external/customer waybill within an order; new shipping ≤ approved ready stock and open net demand; customer return ≤ linked shipment remainder.

## Navigation, feedback, accessibility and consistency

Primary cards, machine links, order→job links, empty-state messages and large production save controls work. Consistent base colors/radii, focus outlines, reduced-motion rules and the skip link provide a useful foundation. However, there is no URL router, deep linking or browser-history handling; back buttons call `go()`, which clears shared search/filter state. The desired complete journeys are mapped in [screen map](UX_SCREEN_MAP.md).

Dialogs have `role=dialog`/`aria-modal` in the main renderer but no accessible title association, focus trap, initial focus or focus restoration. Wizard labels are not associated with inputs except for selected aria-labels. Suggestions lack combobox/listbox semantics and arrow-key selection. The drawing div has role/button/tabindex but only a click handler. The new-job picker uses a different, unstyled backdrop class and lacks the main modal's semantics. No loading state is required for synchronous lists, but asynchronous file reads have no progress state and save failure is not propagated. Success toasts can coexist with failed persistence. Production-event reasons/details are stored but omitted from `eventsMarkup`.

Turkish terminology varies: “Good/sağlam,” “rework,” “hurda/fire,” “Sevk/Sevkiyat,” “Fason” versus the logistics screen that also contains material, quality and customer shipping. Completion modal text still says completion transfers work to shipping, despite the new final-approval model. The UX-03/04 operator warning says physical receipt/inspection locks are unfinished even where UX-05 now enforces some of them. This obscures which action is authoritative.

## Roadmap and exit criteria

1. **Establish one trusted domain model (P0).** Decide authoritative lots, stock locations, quality states, operation instances, planned allocations and immutable movement IDs. Preserve legacy data explicitly as historical snapshots; design versioned migration and backup before applying it. Make reconciliation pure and exhaustive, then route all shipment APIs through the same final-QA and terminal-operation gate.
2. **Complete planning and physical journeys (P0/P1).** Operation-specific job creation, split quantities, operator assignment, separate reservation/receipt, controlled physical transfers and acceptance, urgent interruption, machine-change history, compensation planning. Exit: the 25 physical and 50 planned remainders can move independently with no double use.
3. **Complete quality, supplier and customer loops (P1).** Dedicated queues, per-operation inspection policies, traceable rework, supplier outcome reconciliation and authorized discrepancy closure, final approved ready stock, shipment reversal, return quarantine/disposition and reopening. Exit: every quantity has a location, quality and provenance through customer return.
4. **Repair navigation and responsive UX (P1/P2).** Contextual links and retained filters, correct job identity, mobile access to all required queues, dashboard component CSS, contained audit scrolling, accessible forms/dialogs, workshop touch targets and clear Turkish vocabulary. Exit: all requested navigation paths pass at 1440/390/360.
5. **Production readiness (release gate).** Move persistence and permissions to a transactional shared service if multi-user use is intended; versioned recovery/import/export and CI regression gates. Retire or redirect the separate sales app. Exit: concurrent reservations/shipments cannot overspend stock and unauthorized mutations fail in the service, not just UI.

No backlog implementation is included. Specific issues and acceptance criteria are in [gap backlog](UX_GAP_BACKLOG.md).
